# HA Video Call Bridge

A small Windows service that detects active Zoom and Google Meet calls and publishes their state to Home Assistant over MQTT.

The bridge was created to automate an office LED status sign, but the MQTT entities can be used by any Home Assistant automation.

## Architecture

The bridge combines two independent call detectors:

- **Google Meet**: a Firefox extension detects whether an actual Meet call is active and reports that state to the local bridge over WebSocket.
- **Zoom**: the bridge monitors the IPCSDK log generated by the official Elgato Stream Deck Zoom plugin.

The combined video-call state is published to Home Assistant through MQTT Discovery.

Home Assistant is responsible for deciding what to do with the detected call state. The bridge does not directly control the office sign.

## Detectors

### Google Meet

Google Meet detection uses the included Firefox extension:

```text
firefox-extension/
├── manifest.json
└── meet_state_bridge.js
```

The extension runs only on:

```text
https://meet.google.com/*
```

It checks for the Google Meet **Leave Call** control:

```text
[jsname="CQylAd"]
```

The presence of that control indicates that the browser tab is currently participating in a meeting.

This is intentionally different from simply detecting whether a Google Meet page is open. The Meet home page and pre-join screen are not considered active calls.

### Google Meet WebSocket

The Firefox extension reports its state to the Windows bridge over a local WebSocket connection:

```text
ws://127.0.0.1:2395
```

The extension sends only call-state information:

```json
{
  "type": "meet_state",
  "client_id": "...",
  "active": true
}
```

It does not send the meeting URL.

Each Meet tab is tracked independently. Google Meet is considered active if **any connected Meet tab** reports an active call.

If the connection to the bridge is lost, the extension attempts to reconnect automatically and reports its current state again after reconnecting.

### Firefox Extension Installation

The extension is packaged and Mozilla-signed as a private/self-distributed Firefox add-on.

The signed `.xpi` file can be installed permanently in Firefox.

The extension manifest uses the Gecko extension ID:

```text
ha-google-meet-state-bridge@local
```

The currently deployed extension version is:

```text
1.0.0
```

After installation, the extension automatically runs on Google Meet pages. No Stream Deck Google Meet plugin is required for call detection.

### Zoom

Zoom detection uses the IPCSDK log generated by the official Elgato Stream Deck Zoom plugin.

The plugin executable is normally located at:

```text
%APPDATA%\Elgato\StreamDeck\Plugins\com.elgato.zoom.sdPlugin\bin\ESDZoom.exe
```

The IPCSDK log directory is:

```text
%APPDATA%\IPCSDK\logs
```

The bridge watches the newest:

```text
ToolSuite_*.log
```

file and automatically follows new files when the Zoom IPCSDK rotates its logs.

Observed meeting states:

```text
eStatus :1 = connecting / inactive
eStatus :3 = active meeting
eStatus :4 = leaving / inactive
eStatus :7 = meeting ended / inactive
```

Only status `3` is considered an active Zoom call.

## Combined Call State

The bridge maintains independent states for:

```text
Google Meet
Zoom
```

The combined video-call state is active whenever either detector is active:

```text
Meet ON  OR  Zoom ON
        ↓
Video Call ON
```

When neither detector is active:

```text
Meet OFF AND Zoom OFF
        ↓
Video Call OFF
```

## MQTT

The bridge publishes retained state to:

```text
office/video_call/meet
office/video_call/zoom
office/video_call/active
office/video_call/status
```

The detector state values are:

```text
ON
OFF
```

The status topic publishes:

```text
online
offline
```

The combined `office/video_call/active` topic is `ON` whenever either Google Meet or Zoom is active.

## Home Assistant MQTT Discovery

The bridge automatically publishes MQTT Discovery configuration for three binary sensors:

```text
Google Meet
Zoom
Video Call
```

They appear under a single MQTT device:

```text
Video Call Bridge
```

Device information currently identifies the bridge as:

```text
Manufacturer: Custom
Model: Windows Video Call Bridge
Firmware: 1.1.0
```

The combined entity currently used by the office-sign automation is:

```text
binary_sensor.video_call_bridge_video_call
```

Home Assistant entity IDs should still be verified after MQTT Discovery rather than assumed on a new installation.

## Installation

### 1. Create a Virtual Environment

From the repository root:

```powershell
py -m venv .venv
```

Activate it:

```powershell
.\.venv\Scripts\Activate.ps1
```

### 2. Install Dependencies

```powershell
python -m pip install -r requirements.txt
```

The current Python dependencies are:

```text
paho-mqtt>=2.1,<3
websockets>=15,<16
```

### 3. Create the Configuration

Copy:

```text
config.example.ini
```

to:

```text
config.ini
```

Enter the MQTT configuration and credentials in `config.ini`.

Do not commit `config.ini`.

### 4. Install the Firefox Extension

Install the Mozilla-signed Google Meet bridge `.xpi` in Firefox.

The extension connects automatically to:

```text
127.0.0.1:2395
```

when a matching Google Meet page is open.

### 5. Test the Bridge Manually

From the repository root:

```powershell
python .\src\bridge.py
```

Verify that the bridge:

1. Starts the Google Meet WebSocket server.
2. Connects to the MQTT broker.
3. Publishes Home Assistant MQTT Discovery.
4. Locates the Zoom IPCSDK logs.
5. Responds correctly when joining and leaving Google Meet and Zoom calls.

Press `Ctrl+C` to stop the manually launched bridge.

## Automatic Startup

The bridge is normally launched automatically with Windows Task Scheduler.

The configured task is:

```text
HA Video Call Bridge
```

### Program

```text
C:\Users\Administrator\projects\ha-video-call-bridge\.venv\Scripts\pythonw.exe
```

### Arguments

```text
C:\Users\Administrator\projects\ha-video-call-bridge\src\bridge.py
```

### Start In

```text
C:\Users\Administrator\projects\ha-video-call-bridge
```

The task is configured to:

- Run at user logon.
- Delay startup by 30 seconds.
- Run only while the user is logged on.
- Run with highest privileges.
- Prevent multiple simultaneous instances.
- Continue running in the background.

`pythonw.exe` is used so the bridge can run without leaving a console window open.

## Expected Operation

When the bridge is running, Home Assistant should show the `Video Call Bridge` MQTT device as available.

Joining a Google Meet call should result in:

```text
Google Meet = On
Video Call  = On
```

Leaving the meeting should result in:

```text
Google Meet = Off
Video Call  = Off
```

Joining a Zoom meeting should result in:

```text
Zoom       = On
Video Call = On
```

Leaving the Zoom meeting should result in:

```text
Zoom       = Off
Video Call = Off
```

The combined state remains `ON` if one detector becomes inactive while the other is still active.

## Home Assistant Integration

The bridge only reports video-call state.

Home Assistant is responsible for interpreting that state and controlling the office sign.

The current office-sign behavior distinguishes between scheduled and unscheduled calls.

### Scheduled Calls

When a Class calendar appointment is active, the calendar owns the display:

```text
IN CLASS
TIL <end time>
```

Starting Zoom or Google Meet during that appointment does **not** replace the calendar message with `VIDEO CALL`.

Instead, the video-call state confirms that an actual call occurred during the scheduled appointment.

If the call disconnects, Home Assistant keeps the calendar message displayed during a configurable reconnect grace period.

If the call reconnects during that period, the appointment continues normally.

If it does not reconnect, Home Assistant considers that individual appointment ended early and turns the display off.

### Unscheduled Calls

When no Class calendar appointment is controlling the sign, an active Zoom or Google Meet call displays:

```text
VIDEO CALL
```

When the call ends, Home Assistant restores the display state that existed before the unscheduled call.

For example:

```text
AVAILABLE → VIDEO CALL → AVAILABLE
```

or:

```text
OFF → VIDEO CALL → OFF
```

This separation keeps call detection independent from sign-display policy.

## Security

MQTT credentials must not be stored in source code.

Real credentials belong only in:

```text
config.ini
```

which is excluded by `.gitignore`.

A dedicated non-administrator Home Assistant/MQTT account should be used for the bridge rather than a personal or administrator account.

The Firefox extension communicates only with the bridge on localhost:

```text
127.0.0.1:2395
```

The extension reports call state only and does not send the Google Meet URL.

## Troubleshooting

### Google Meet Does Not Change State

Verify:

1. The Windows bridge is running.
2. The signed Firefox extension is installed and enabled.
3. The Meet page is running in Firefox.
4. An actual meeting has been joined, rather than only opening the Meet home or pre-join page.
5. Nothing else is preventing the local WebSocket connection on port `2395`.

Restarting Firefox should not require restarting the bridge. The extension reconnects automatically.

### Zoom Does Not Change State

Verify that the official Elgato Zoom Stream Deck plugin is installed and that IPCSDK logs exist under:

```text
%APPDATA%\IPCSDK\logs
```

Look for:

```text
ToolSuite_*.log
```

The bridge automatically follows log rotation, so the newest log file may change between meetings.

### Home Assistant Does Not Update

Verify:

1. The MQTT broker is running.
2. The credentials in `config.ini` are correct.
3. The bridge reports a successful MQTT connection.
4. MQTT Discovery is enabled in Home Assistant.
5. The `Video Call Bridge` device is available in Home Assistant.

## Current Scope

The bridge is responsible only for:

- Detecting active Google Meet calls.
- Detecting active Zoom calls.
- Combining those detector states.
- Publishing the states through MQTT.
- Publishing Home Assistant MQTT Discovery.

Home Assistant remains responsible for:

- Calendar scheduling.
- Reconnect grace periods.
- Determining whether a call is scheduled or unscheduled.
- Deciding what the office sign should display.
- Restoring the previous sign state after unscheduled calls.
- Handling appointments that end early.

Keeping those responsibilities separate allows the Windows bridge to remain a small call-state detector while Home Assistant acts as the automation and display-control layer.
